# Documentation Rules

## Context

Documentation exists to preserve decisions, requirements, business rules, and behavior that are not obvious from the code.
It should remain concise and synchronized with the implementation.

## Rules

- Keep documentation concise and actionable.
- Document decisions, business rules, architecture, and behavior; do not document obvious code.
- Keep documentation synchronized with the implementation.
- Update existing documentation when changing documented behavior.
- Prefer updating an existing document over creating a duplicate.
- Use relative links for project documentation.
- Use examples only when they clarify behavior or usage.
- Do not claim a feature, rule, API, or behavior that is not implemented.
- When requirements are unknown, mark them as undefined instead of inventing them.
